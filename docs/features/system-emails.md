# Feature: System Emails (full section)

Decided 2026-10-25 (PROJECT.md). Backend built 2026-10-25 (see "Built" below; screens come from the frontend). Own branch after `feature/system-code-view` (and after Approval, which takes the approver settings out of Emails).

## 1. Automatic emails
- List of every automatic email (verify, welcome, password reset, team invite, Gold ack/approver/invite/active, later booking emails): when it is sent, subject, last edited.
- Edit subject and wording in plain text with placeholders ({first_name}, {plan_name}, {opening}...), checked before saving (unknown placeholder = error). Live preview in the real email layout, desktop and phone width. **Send me a test** to the signed-in developer.
- Logged with undo like every System change. Contact address and Gold approver CC stay here.

## 2. Send to a group
- Groups built from data: everyone registered, by tier, Gold members, opted in to news, email not confirmed yet, registered in a date range, Gold applicants by status, and **Journey leads**. Shows the count before sending.
- **Journey leads** (`people = "leads"`, News only): addresses left at the journey gate (`JourneySession.lead_email`, any browser or case, one row per address) with no account (staff included), not a bot session, not on `EmailOptOut`, not in `EmailSuppression`, address not erased. Optional "Given from / to" dates (`lead_at`). The gate tick is the consent. A Service send is refused for this group (they never registered, so no service reason). Rows have no user id and first name "there"; they get the same News footer unsubscribe link and headers. `/unsubscribe/<token>/` puts the address on `EmailOptOut`, which drops it from the group. At send time a lead who has since registered is judged by his account's news choice. Ticking news when registering clears the opt-out (`optout.clear`).
- Marketing emails go only to people opted in (`marketing_opt_in`), always with a one-click unsubscribe link (and List-Unsubscribe header). Service messages (e.g. "booking opens") may go to all members, chosen explicitly per send.
- Write, preview, send a test, schedule or send now. Sent in batches by the background worker within the SES rate. Suppressed addresses are skipped.
- **Only when SES production access is approved** (read from AWS `GetAccount.ProductionAccessEnabled`, cached; System > Emails shows the state). Until then Send is disabled with a clear message.

## 3. Invites
- Paste or upload a list (CSV) of names and addresses (the emails people already sent Moishe). The check has two levels, see "Invite import hardening (2026-10-29)" below.
- Sends a "Register for Spa 99" invite with a personal link; tracks sent, opened link, registered.
- Same SES production rule as group sends.

## Notes
- Everything logged (who sent what to how many).
- Before the first bulk send, tell AWS (support case) that opted-in announcements are added, with unsubscribe and suppression handling, so the account stays in good standing.

## Built (2026-10-25, backend; the frontend builds the screens)

**Apps and files.** New app `mailings` (models, `segments.py`, `sending.py`, `invites.py`, `tokens.py`, `optout.py`, public `views.py`). Wording and SES gate in `notifications` (`emailbody.py`, `ses.py`). System pages in `system/views_emails.py` (logic `system/emails.py`), minimal unstyled templates `system/templates/system/emails*.html` (hooks are `data-system-*`). Nothing is Postgres-only (plain ORM, `bulk_create(ignore_conflicts)`, conditional `update()`); not run against Postgres locally, CI covers it.

**Models (schema-only migrations: `notifications.0005`, `mailings.0001`, `system.0009` choices).**
- `NotificationTemplate.body` (blank = built-in default), `EmailLog.message_id`.
- `Mailing`: name, subject, body, `kind` news|service, `group` + `params` JSON, `status` draft|scheduled|sending|sent|cancelled|failed, scheduled_at, started_at, finished_at, error, created_by, total/sent/skipped/failed counts.
- `MailingRecipient`: mailing, email, first_name, user (null), `status` queued|sending|sent|skipped|failed|bounced, reason, sent_at, message_id; unique (mailing, email).
- `Invite`: name, email (lower), token (24 random bytes, unique), `status` queued|sending|sent|opened|registered|bounced|skipped|failed, reason, batch_id, sent_at, opened_at, registered_at, registered_user, expires_at (created + 30 days), message_id, created_by. `queued`, `sending` and `failed` are extra to the spec: they are the states before and during sending.
- `EmailOptOut` (email, source): an address that unsubscribed **without an account**. Chosen over `EmailSuppression` because an unsubscribe is not a bounce or complaint and must not stop service messages; it is its own flag, kept like a suppression (address only). People with an account use `User.marketing_consent` (history logged, shows in My Spa 99). Choosing news again (account switch, ticking the box when registering) clears the opt-out.

**Automatic emails.** `notifications/emailbody.py` holds `SPECS` (per key: placeholders with descriptions, sample values, default body, button label, required button). Body is plain text: blank line = paragraph, `{placeholder}`, `{button}` = the main link as the button (plain text: the address on its own line). The text is escaped, values are escaped, only `*_url` values become links. Layout files are `_base.html`, `_body.html`, `_body.txt` (the seven editable emails and `invite`/`mailing` use `_body`; the per-email template files are gone, their wording is the `default_body` in code). Stored body that no longer validates, or blank, falls back to the default, so a send never fails. Subject placeholders: `{first_name}` (callers pass it now) and `{name}`/`{potential}` for the Gold approver emails. **Subject-only** (layout is a real application): `gold_approver`, `gold_approver_repeat`, `gold_final`, `gold_sent_back`; no test send for them. A body equal to the default is stored blank. **`{valid_for}`** (2026-10-27) is a computed placeholder in verify, gold_invite and invite: how long the link works in plain words, from System > Defaults (or the length stamped on the invite row); listed in the placeholder help, accepted by validation, filled in previews, test sends and real sends (`SPECS[...].values`). New key `invite` (seeded subject). Editable: verify, welcome, password_reset, team_invite, gold_ack, gold_invite, gold_active, invite.

**Groups** (`mailings/segments.py`, `GROUPS`, `catalog()`, `clean_params()`, `count()`, `rows()`): `everyone`, `tier` (param `plan` slug), `gold`, `opted_in`, `unconfirmed`, `between` (`date_from`, `date_to`, either optional), `applicants` (param `status`). "Registered" = active user with a registered interest (team accounts without one are not). Always out: suppressed (case-insensitive), inactive. News also needs consent (the application's tick for applicants) and drops `EmailOptOut`.

**Sending flow.** `sending.start()`: SES gate, checks (text valid, group valid, count > 0), claims draft->sending with a conditional update, snapshots the group into `MailingRecipient` (once), writes `mailing_sent`, queues `mailings.tasks.send_mailing`. The task works in slices of about 60 s: for each queued row it claims it (queued->sending, conditional), re-checks consent, opt-out, active, sends through `send_templated` (suppression guard, `EmailLog`), marks sent/skipped/failed, paced to `MAILING_RATE_PER_SECOND` (settings constant, default 10, never above SES `MaxSendRate`; no pacing when the queue runs inline in dev), then queues itself again until none are queued, then marks sent (failed if nothing was sent and some failed). A row stuck in `sending` for 5 minutes (dead worker) is marked failed, never retried, so nobody gets it twice. "Carry on sending" (`resume`) just queues the worker again. Cancel: scheduled or sending -> cancelled, queued rows become skipped. Schedule: a django-q one-off `Schedule` named `mailing-<id>` calling `mailings.tasks.start_scheduled`; if SES is not allowed at that time the mailing goes back to draft with `error`.
- News: footer link to `/unsubscribe/<token>/` (signed, salt `spa99.mailings.unsubscribe`, no expiry), headers `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, line "You are receiving this because you opted in to news".
- Service: no unsubscribe, line "You are receiving this message because you registered with Spa 99" (Gold applicants: "because you applied for a Spa 99 Gold Card").
- Invites carry the unsubscribe link and headers too (they are marketing to people who never opted in) and skip addresses on `EmailOptOut`.

**Invites.** `mailings/invites.py`: `check(text_or_bytes)` -> report `{rows:[{line,name,email,status,message}], counts, errors, ok, total}`; status ok | invalid | duplicate | member | invited (pending, unexpired) | suppressed | opted_out. Tolerant parsing: header row, `,` `;` tab, quotes, `Name <email>`, either column order, BOM, blank lines. Limits: 2000 rows, 1 MB (whole list refused with an error). `create_batch()` re-checks and writes `queued` invites (ok rows) and `skipped` ones (valid but not invitable, with reason); invalid and repeated rows live only in the report. Public `/invite/<token>/` (rate limited 60/min/IP): marks `opened` (never downgrades), keeps the token in the session and redirects to `/register/`, which pre-fills first name, last name and email from it (nothing in the URL). Unknown, expired and not-yet-sent links just redirect to Register. Registering (`register_interest`) marks pending invites for that address `registered`. A hard bounce or complaint marks sent/opened invites and recent mailing rows `bounced`.

**SES gate.** `notifications.ses_status()` -> `{mode: production|sandbox|dev|unknown, max_24h, sent_24h, max_rate, allowed, message}` from boto3 `sesv2.get_account()`, cached 1 hour (unknown: 2 minutes), never raises. `dev` = DEBUG or console/locmem/file/dummy backend: allowed, no AWS call. `require_sending_allowed()` raises `SendingRefused` (plain message). Used by mailing start/schedule and invite start.

**Endpoints** (System host, Developer, unlocked, CSRF; a form POST redirects with a toast, a script sending `Accept: application/json` or `X-Requested-With: fetch` gets JSON `{ok, message, ...}`):
- `GET /emails/` overview, context `ses`, `stats {sent_today, sent_week, failed_week, bounces_week, complaints_week, suppressed_total, unsubscribed_no_account}`, `recent_mailings`, `recent_invite_batches`, plus the existing `form` (CC, contact) and `risky_fields`. `POST /emails/ses/refresh/` reads SES now (6 per 10 min).
- `GET /emails/automatic/` -> `emails [{key, title, when, editable, subject, default_subject, subject_changed, body_changed, last_edited_at, last_edited_by}]`.
- `GET /emails/automatic/<key>/` -> `spec {key, title, editable, has_button, button_required, button_label, placeholders [{name, description, sample}], subject_placeholders}`, `form` (subject, body, row_token), `row`, `default_subject`, `default_body`, `is_default`. `POST .../save/` (400 field errors, 409 stale, toast with undo), `POST .../preview/` (subject, body -> `{ok, subject, html (full email document), text, errors}`; errors come back with status 200 and empty html), `POST .../test/` (to the signed-in developer, `[Test]` prefix, 5 per 10 min per person, `email_test` event), `POST .../reset/` (subject and body back to default, one logged undoable change).
- Mailings: `GET /emails/mailings/` (`mailings` page, `ses`), `GET|POST /emails/mailings/new/`, `GET|POST /emails/mailings/<id>/edit/` (draft only; form fields name, subject, body, kind, group plus the group's option fields named after `groups[].params[].name`; context `groups` = `segments.catalog()` with each param's `value`, `kind_choices`, `placeholders`, `count_url`, `preview_url`), `GET /emails/mailings/count/?group=&kind=&plan=...` -> `{count, errors}`, `POST /emails/mailings/preview/` (subject, body, kind, group -> as the automatic preview, with the unsubscribe line or the "why" line), `GET /emails/mailings/<id>/` (`mailing`, `progress`, `live_count`, `blockers`, `can_send`, `ses`, `recipients` page, `progress_url`, `preview`), `GET .../progress/` -> `{status, status_label, total, sent, bounced, skipped, failed, queued, sending, percent, finished, started_at, finished_at, error}`, `POST .../test/`, `.../send/` (optional `expected_count`: refused if the group changed), `.../schedule/` (`scheduled_at` as `YYYY-MM-DDTHH:MM` UK time, at least a minute ahead), `.../cancel/`, `.../resume/`, `.../delete/` (draft only). Starts and schedules: 6 per 10 min per person.
- Invites: `GET /emails/invites/` (`batches`), `GET /emails/invites/new/`, `POST /emails/invites/review/` (`text` or file `file`; context `report`, `text`, `status_labels`; 400 on a file-level error), `POST /emails/invites/send/` (`text`, optional `expected_ok`; checks again, writes the batch, queues the send, redirects to the batch), `GET /emails/invites/<batch>/` (`summary`, `invites` page, `status_filter`), `GET .../progress/` -> counts per status, `POST .../resume/`.
- Public (no login): `GET|POST /unsubscribe/<token>/` (GET confirm page; POST and the one-click POST switch news off, idempotent, CSRF exempt, 30 per minute per IP), `GET /invite/<token>/`.

**Audit.** New `SystemEvent` kinds `mailing_scheduled`, `mailing_sent` (written when sending starts, with recipient count, group and params), `mailing_cancelled`, `invites_sent` (invites and skipped), `email_test`; all section "emails", category "change". Template edits and Reset are in the change log with undo. Mailings and invites hold addresses: erased and exported with the person (`delete_user_data`, `export_user_data`); the opt-out and suppression lists keep only the address.

**Limits and notes.** Rate 10 a second by default. Mailing body 5000 characters, subject 300. Group count and sends read stored rows; the recipient list is a snapshot when sending starts. The Django admin has read-only lists with CSV export for mailings, recipients, invites and opt-outs. The code view is unchanged (the Emails adapter edits the recipients only; templates are not in it). No new env vars.

### Review fixes (2026-10-25)

- **Unsubscribe link is opaque.** `mailings.UnsubscribeKey` (one random key per address, migration `mailings.0002`): no address in any URL. Old signed tokens no longer work. Erased with the person (`mailings/erasure.py`), also when a Gold application is erased (`gold.services.delete_applications`), so group-send rows and invites for an applicant with no account go too. `EmailOptOut` stays.
- **Gate on every slice.** `resume()` and `start_invites_resume()` need `require_sending_allowed()`. Each `run_mailing` / `run_invites` slice checks it first; if SES refuses, the mailing goes to the new status `paused` with the reason in `mailing.error` (Resume continues, Cancel works); invites simply stay queued and the slice returns "paused".
- **Opened is marked when Register renders** with the invite in the session (`invites.prefill`), not on the `/invite/<token>/` redirect.
- **Throttling.** A send that fails with Throttling, MaxSendingRateExceeded, 5xx or a network timeout goes back to `queued` with `retry_at` (30 s, 60 s, 120 s ...) and `attempts` (fails after 5); the slice eases off for a second. One worker per mailing or invite batch (a cache lock shared through the database cache, freed after 2 minutes if a worker dies), so two workers cannot double the rate; a second one answers "busy".
- Blank first name falls back to "there" in subjects too. Gold account set-up now marks invites registered (and clears an old unsubscribe when news is ticked), through the same hook as Register. Team accounts are not members and are left alone.

## Two new automatic emails (2026-10-26, Gold actions)

Both are listed in System > Emails > Automatic emails (editable subject and wording, preview, test send, reset) and both go through `send_templated`, so they use the shared layout, the suppression guard, the email log, and Reply-To = the site contact address.

- **`gold_respond`** ("A message about your Spa 99 Gold Card application"). Sent when an approver clicks Respond on a Gold application. Placeholders `{first_name}` and `{message}` (what the approver typed; line breaks kept; escaped). Default body: "Hello {first_name}, {message}, You can reply to this email and it will reach the team." Sent from `gold.tasks.send_gold_applicant_email(application_id, event_id)` (ids only; the text is read from the audit event, so no applicant text sits in the queue).
- **`gold_declined`** ("Your Spa 99 Gold Card application"). Only sent when the approver ticks **Email the applicant** while declining (default off; whether declines get an email is still Moishe's decision). Placeholders `{first_name}`, `{name}`, `{reference}`. The editable wording **prefills** the decline form's message box (placeholders filled in); the approver can change it, and what is sent is exactly the text in the box (shown as typed in the shared layout, `send_templated(..., plain_body=...)`). The sent result is a line in the application's History.

The Gold approver email and the "sent back" email gained **Decline** and **Respond** links (Office form, `?do=decline|respond`); their wording stays in the template files (subject only is editable).

## Postmark bounces (2026-10-27)

With Postmark sending, permanent bounces and spam complaints arrive at `POST /postmark/webhook/` and land in the same suppression list as SES feedback, so group sends, invites and account emails skip those addresses and the System > Emails stats count them. Details and setup: `docs/features/email.md`.

## Password changed email (2026-10-27)

New editable automatic email `password_changed` ("Your Spa 99 password was changed"; placeholders `{first_name}`, `{when}` London time, `{reset_url}`; no button, plain link line "If this wasn't you, reset your password now"; Reply-To is the contact address). Seeded by `notifications/seed.py` like the others (`seed_phase1` adds the missing row; no migration, no backfill). Sent by the task `users.tasks.send_password_changed_email(user_id, when_iso)` through `send_templated` (suppression guard, EmailLog, never raises), queued by `users.services.password_changed(user)`.
- Hooks: `_PasswordChange.form_valid` (member area and the Office, System and Control change-password pages, so team accounts too) and `users.services.reset_password` (reset completion).
- No email for a first password: if the account had no usable password before (a team invite or Gold set-up), nothing is sent. Nothing for admin or command password sets (they do not call the helper).
- `{reset_url}` is always the public `SITE_URL/forgot-password/` page (every account can use it). No device or IP is included.

## Invite import hardening (2026-10-29)

Moishe imports the emails people already sent him; each gets an invite to register. Code: `mailings/invites.py`, views in `system/views_emails.py`, `system/templates/system/emails_invites_review.html`, review script in `common/static/common/js/system-emails.js`. New model `mailings.InviteImport` (migration `mailings.0006`, schema only). No new env vars; nothing Postgres-only.

**Two levels.** The review page shows a summary line ("123 will be invited · 4 skipped · 3 repeated rows merged · 2 need fixing") and, per category, the count and the row numbers (row 1 is the header; numbers match the file).
- **Errors** (the import button is off until fixed): file unreadable (not text, an `.xlsx`, bad encoding), no email column, empty, over 2000 rows or 1 MB; per row: `invalid` address (also a name over 100 characters), `unsafe` (any cell of the row starts with `=` `+` `-` `@`, so Excel could run it as a formula), `ambiguous` (one address on several rows with different names: every such row is flagged, none is imported).
- **Warnings** (allowed; stated beside the row): `duplicate` (exact repeat of an earlier row, imported once), `case_duplicate` (same address with different case or spaces, same name, imported once), `member`, `invited` (pending and not expired), `suppressed`, `opted_out` (all skipped), and a missing name (still `ok`, imported with a blank name, counted as `no_name`). The same name on different addresses is fine and not flagged. A blank-name row and a named row for one address are the same person (the name is kept).
- Report keys: `rows[{line,name,email,status,level,message,no_name}]`, `counts`, `errors` (file level), `ok`, `total`, `problems`, `warnings`, `blocked`, `can_import`, `groups[{key,label,level,count,lines}]`, `summary`, `skipped`, `merged`. `create_batch` writes nothing while `blocked`. Skipped invites are still written (status `skipped`, with the reason) for member, invited, suppressed and opted-out rows.

**Reading files.** UTF-8 with or without BOM, UTF-16 with BOM, else Windows-1252 (Excel); `,` `;` or tab (chosen on the first line, ignoring quoted parts); quoted cells including line breaks inside quotes; `\r`, `\r\n` or `\n` line ends; spaces trimmed. Header optional and tolerant: email column = Email, E-mail, Email Address, Mail; name = Name, Full name, or First name (+ Last name); either column order. Without a header the cell with an `@` is the address (also `Name <a@b.c>`). A first row that names columns but has no email column is a file error.

**Double submit.** Drawing a review with nothing to fix issues a one-time `InviteImport` row (random token, the signed-in user, SHA-256 of the list with line ends normalised, no addresses). Import (`POST /emails/invites/send/`) needs `token` and `text`: unknown token, another person's token, or a list that does not hash to the checked one is refused ("Check the list again"). The first confirmation claims the token with one conditional UPDATE (`batch_id IS NULL`) inside the same transaction that writes the batch, so concurrent or repeated requests make exactly one batch; any later request with that token answers with the existing batch (`repeated: true`), sends nothing and writes no second audit event. The token check and the repeat answer come before the list is re-checked (its people are by then "invited"). Unused tokens older than 7 days are deleted when a new one is issued. Client side: the button is guarded while the confirm is open, disables and says "Importing..." on submit, a second submit is ignored, and a Back-button return re-enables it (the server still answers a repeat with the same batch).

**Review page.** Inline fix box for invalid addresses (Check re-reviews the list and a fresh token is issued); filter chips per category; "Download problem rows (CSV)" (`POST /emails/invites/problems/`, `text`; columns Row, Level, Name, Email, What to do; cells starting with `= + - @` get a leading apostrophe); "Start again" to upload a fixed file.

**Endpoints.** `POST /emails/invites/review/` (context adds `token`; empty when there is nothing importable), `POST /emails/invites/send/` (`text`, `token`, optional `expected_ok`; JSON adds `repeated`), `POST /emails/invites/problems/`. All Developer, unlocked, CSRF.
