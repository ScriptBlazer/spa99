# Feature: System Emails (full section)

Decided 2026-10-25 (PROJECT.md). Backend built 2026-10-25 (see "Built" below; screens come from the frontend). Own branch after `feature/system-code-view` (and after Approval, which takes the approver settings out of Emails).

## 1. Automatic emails
- List of every automatic email (verify, welcome, password reset, team invite, Gold ack/approver/invite/active, later booking emails): when it is sent, subject, last edited.
- Edit subject and wording in plain text with placeholders ({first_name}, {plan_name}, {opening}...), checked before saving (unknown placeholder = error). Live preview in the real email layout, desktop and phone width. **Send me a test** to the signed-in developer.
- Logged with undo like every System change. Contact address and Gold approver CC stay here.

## 2. Send to a group
- Groups built from data: everyone registered, by tier, Gold members, opted in to news, email not confirmed yet, registered in a date range, Gold applicants by status. Shows the count before sending.
- Marketing emails go only to people opted in (`marketing_opt_in`), always with a one-click unsubscribe link (and List-Unsubscribe header). Service messages (e.g. "booking opens") may go to all members, chosen explicitly per send.
- Write, preview, send a test, schedule or send now. Sent in batches by the background worker within the SES rate. Suppressed addresses are skipped.
- **Only when SES production access is approved** (read from AWS `GetAccount.ProductionAccessEnabled`, cached; System > Emails shows the state). Until then Send is disabled with a clear message.

## 3. Invites
- Paste or upload a list (CSV) of names and addresses; duplicates and existing members are flagged and skipped.
- Sends a "Register for Spa 99" invite with a personal link; tracks sent, opened link, registered.
- Same SES production rule as group sends.

## Notes
- Everything logged (who sent what to how many).
- Before the first bulk send, tell AWS (support case) that opted-in announcements are added, with unsubscribe and suppression handling, so the account stays in good standing.

## Built (2026-10-25, backend; the frontend builds the screens)

**Apps and files.** New app `mailings` (models, `segments.py`, `sending.py`, `invites.py`, `tokens.py`, `optout.py`, public `views.py`). Wording and SES gate in `notifications` (`emailbody.py`, `ses.py`). System pages in `system/views_emails.py` (logic `system/emails.py`), minimal unstyled templates `system/templates/system/emails*.html` (hooks are `data-system-*`). Nothing is Postgres-only (plain ORM, `bulk_create(ignore_conflicts)`, conditional `update()`); not run against Postgres locally, CI covers it.

**Models (schema-only migrations: `notifications.0005`, `mailings.0001`, `system.0009` choices).**
- `NotificationTemplate.body` (blank = built-in default), `EmailLog.message_id`.
- `Mailing`: name, subject, body, `kind` news|service, `group` + `params` JSON, `status` draft|scheduled|sending|sent|cancelled|failed, scheduled_at, started_at, finished_at, error, created_by, total/sent/skipped/failed counts.
- `MailingRecipient`: mailing, email, first_name, user (null), `status` queued|sending|sent|skipped|failed|bounced, reason, sent_at, message_id; unique (mailing, email).
- `Invite`: name, email (lower), token (24 random bytes, unique), `status` queued|sending|sent|opened|registered|bounced|skipped|failed, reason, batch_id, sent_at, opened_at, registered_at, registered_user, expires_at (created + 30 days), message_id, created_by. `queued`, `sending` and `failed` are extra to the spec: they are the states before and during sending.
- `EmailOptOut` (email, source): an address that unsubscribed **without an account**. Chosen over `EmailSuppression` because an unsubscribe is not a bounce or complaint and must not stop service messages; it is its own flag, kept like a suppression (address only). People with an account use `User.marketing_consent` (history logged, shows in My Spa 99). Choosing news again (account switch, ticking the box when registering) clears the opt-out.

**Automatic emails.** `notifications/emailbody.py` holds `SPECS` (per key: placeholders with descriptions, sample values, default body, button label, required button). Body is plain text: blank line = paragraph, `{placeholder}`, `{button}` = the main link as the button (plain text: the address on its own line). The text is escaped, values are escaped, only `*_url` values become links. Layout files are `_base.html`, `_body.html`, `_body.txt` (the seven editable emails and `invite`/`mailing` use `_body`; the per-email template files are gone, their wording is the `default_body` in code). Stored body that no longer validates, or blank, falls back to the default, so a send never fails. Subject placeholders: `{first_name}` (callers pass it now) and `{name}`/`{potential}` for the Gold approver emails. **Subject-only** (layout is a real application): `gold_approver`, `gold_approver_repeat`, `gold_final`, `gold_sent_back`; no test send for them. A body equal to the default is stored blank. New key `invite` (seeded subject). Editable: verify, welcome, password_reset, team_invite, gold_ack, gold_invite, gold_active, invite.

**Groups** (`mailings/segments.py`, `GROUPS`, `catalog()`, `clean_params()`, `count()`, `rows()`): `everyone`, `tier` (param `plan` slug), `gold`, `opted_in`, `unconfirmed`, `between` (`date_from`, `date_to`, either optional), `applicants` (param `status`). "Registered" = active user with a registered interest (team accounts without one are not). Always out: suppressed (case-insensitive), inactive. News also needs consent (the application's tick for applicants) and drops `EmailOptOut`.

**Sending flow.** `sending.start()`: SES gate, checks (text valid, group valid, count > 0), claims draft->sending with a conditional update, snapshots the group into `MailingRecipient` (once), writes `mailing_sent`, queues `mailings.tasks.send_mailing`. The task works in slices of about 60 s: for each queued row it claims it (queued->sending, conditional), re-checks consent, opt-out, active, sends through `send_templated` (suppression guard, `EmailLog`), marks sent/skipped/failed, paced to `MAILING_RATE_PER_SECOND` (settings constant, default 10, never above SES `MaxSendRate`; no pacing when the queue runs inline in dev), then queues itself again until none are queued, then marks sent (failed if nothing was sent and some failed). A row stuck in `sending` for 5 minutes (dead worker) is marked failed, never retried, so nobody gets it twice. "Carry on sending" (`resume`) just queues the worker again. Cancel: scheduled or sending -> cancelled, queued rows become skipped. Schedule: a django-q one-off `Schedule` named `mailing-<id>` calling `mailings.tasks.start_scheduled`; if SES is not allowed at that time the mailing goes back to draft with `error`.
- News: footer link to `/unsubscribe/<token>/` (signed, salt `spa99.mailings.unsubscribe`, no expiry), headers `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, line "You are receiving this because you opted in to news".
- Service: no unsubscribe, line "You are receiving this message because you registered with Spa 99" (Gold applicants: "because you applied for a Spa 99 Gold Card").
- Invites carry the unsubscribe link and headers too (they are marketing to people who never opted in) and skip addresses on `EmailOptOut`.

**Invites.** `mailings/invites.py`: `check(text_or_bytes)` -> report `{rows:[{line,name,email,status,message}], counts, errors, ok, total}`; status ok | invalid | duplicate | member | invited (pending, unexpired) | suppressed | opted_out. Tolerant parsing: header row, `,` `;` tab, quotes, `Name <email>`, either column order, BOM, blank lines. Limits: 2000 rows, 1 MB (whole list refused with an error). `create_batch()` re-checks and writes `queued` invites (ok rows) and `skipped` ones (valid but not invitable, with reason); invalid and repeated rows live only in the report. Public `/invite/<token>/` (rate limited 60/min/IP): marks `opened` (never downgrades), keeps the token in the session and redirects to `/register/`, which pre-fills first name, last name and email from it (nothing in the URL). Unknown, expired and not-yet-sent links just redirect to Register. Registering (`register_interest`) marks pending invites for that address `registered`. A hard bounce or complaint marks sent/opened invites and recent mailing rows `bounced`.

**SES gate.** `notifications.ses_status()` -> `{mode: production|sandbox|dev|unknown, max_24h, sent_24h, max_rate, allowed, message}` from boto3 `sesv2.get_account()`, cached 1 hour (unknown: 2 minutes), never raises. `dev` = DEBUG or console/locmem/file/dummy backend: allowed, no AWS call. `require_sending_allowed()` raises `SendingRefused` (plain message). Used by mailing start/schedule and invite start.

**Endpoints** (System host, Developer, unlocked, CSRF; a form POST redirects with a toast, a script sending `Accept: application/json` or `X-Requested-With: fetch` gets JSON `{ok, message, ...}`):
- `GET /emails/` overview, context `ses`, `stats {sent_today, sent_week, failed_week, bounces_week, complaints_week, suppressed_total, unsubscribed_no_account}`, `recent_mailings`, `recent_invite_batches`, plus the existing `form` (CC, contact) and `risky_fields`. `POST /emails/ses/refresh/` reads SES now (6 per 10 min).
- `GET /emails/automatic/` -> `emails [{key, title, when, editable, subject, default_subject, subject_changed, body_changed, last_edited_at, last_edited_by}]`.
- `GET /emails/automatic/<key>/` -> `spec {key, title, editable, has_button, button_required, button_label, placeholders [{name, description, sample}], subject_placeholders}`, `form` (subject, body, row_token), `row`, `default_subject`, `default_body`, `is_default`. `POST .../save/` (400 field errors, 409 stale, toast with undo), `POST .../preview/` (subject, body -> `{ok, subject, html (full email document), text, errors}`; errors come back with status 200 and empty html), `POST .../test/` (to the signed-in developer, `[Test]` prefix, 5 per 10 min per person, `email_test` event), `POST .../reset/` (subject and body back to default, one logged undoable change).
- Mailings: `GET /emails/mailings/` (`mailings` page, `ses`), `GET|POST /emails/mailings/new/`, `GET|POST /emails/mailings/<id>/edit/` (draft only; form fields name, subject, body, kind, group plus the group's option fields named after `groups[].params[].name`; context `groups` = `segments.catalog()` with each param's `value`, `kind_choices`, `placeholders`, `count_url`, `preview_url`), `GET /emails/mailings/count/?group=&kind=&plan=...` -> `{count, errors}`, `POST /emails/mailings/preview/` (subject, body, kind, group -> as the automatic preview, with the unsubscribe line or the "why" line), `GET /emails/mailings/<id>/` (`mailing`, `progress`, `live_count`, `blockers`, `can_send`, `ses`, `recipients` page, `progress_url`, `preview`), `GET .../progress/` -> `{status, status_label, total, sent, bounced, skipped, failed, queued, sending, percent, finished, started_at, finished_at, error}`, `POST .../test/`, `.../send/` (optional `expected_count`: refused if the group changed), `.../schedule/` (`scheduled_at` as `YYYY-MM-DDTHH:MM` UK time, at least a minute ahead), `.../cancel/`, `.../resume/`, `.../delete/` (draft only). Starts and schedules: 6 per 10 min per person.
- Invites: `GET /emails/invites/` (`batches`), `GET /emails/invites/new/`, `POST /emails/invites/review/` (`text` or file `file`; context `report`, `text`, `status_labels`; 400 on a file-level error), `POST /emails/invites/send/` (`text`, optional `expected_ok`; checks again, writes the batch, queues the send, redirects to the batch), `GET /emails/invites/<batch>/` (`summary`, `invites` page, `status_filter`), `GET .../progress/` -> counts per status, `POST .../resume/`.
- Public (no login): `GET|POST /unsubscribe/<token>/` (GET confirm page; POST and the one-click POST switch news off, idempotent, CSRF exempt, 30 per minute per IP), `GET /invite/<token>/`.

**Audit.** New `SystemEvent` kinds `mailing_scheduled`, `mailing_sent` (written when sending starts, with recipient count, group and params), `mailing_cancelled`, `invites_sent` (invites and skipped), `email_test`; all section "emails", category "change". Template edits and Reset are in the change log with undo. Mailings and invites hold addresses: erased and exported with the person (`delete_user_data`, `export_user_data`); the opt-out and suppression lists keep only the address.

**Limits and notes.** Rate 10 a second by default. Mailing body 5000 characters, subject 300. Group count and sends read stored rows; the recipient list is a snapshot when sending starts. The Django admin has read-only lists with CSV export for mailings, recipients, invites and opt-outs. The code view is unchanged (the Emails adapter edits the recipients only; templates are not in it). No new env vars.
