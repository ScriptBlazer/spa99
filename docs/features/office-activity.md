# Office: Activity

`/activity/` (nav item "Activity", the last item after Gold; Developer and Superuser only; others get the same 403 as other restricted pages, for the page and for `?all=1&page=N`, and the item is not drawn. On a phone it sits last in the account menu with Registered, Gold and Invited). Owner decision: PROJECT.md, 2026-11-11. Code: `office/activity.py`, `office/activity_store.py`, `office/signals.py`, command `rebuild_activity`, model `office.ActivityDay`, view `office.views.activity_page`, templates `activity.html` and `_activity_rows.html`, `office-activity.css`, `office-activity.js` (the range and dates switch), chart specs `days` and `types` in `office-charts.js`. Design: `docs/design/OFFICE.md` (Activity). No new data endpoint: the page and its "Show more" rows are the only ways in, both Developer and up.

## The page

A mini dashboard over the list. One bar at the top (When, Dates, Staff member, Type) applies to everything below it.

- **When**: This week (from Monday 00:00 London), This month (the 1st to now), 30 days (today and the 29 before), All time. The default is System > Defaults > "Activity: default range" (`SiteDefaults.activity_range`, default `week`; schema-only migration `system/0026`); the last one picked is remembered in the session (`office_range_activity`). **Dates** win over When (no When item is checked while they are set; picking a When item clears the dates). Custom dates are not remembered.
- **The change lines** compare whole London days with a period of the same length just before: this week (Monday to today) with last week up to the same weekday, this month with last month up to the same day of the month (a short month stops at its end), 30 days with the 30 days before, dates with the same number of days just before them. Today counts as a whole day on both sides (the stored totals are per day, so there is no time-of-day cut). All time has no change line. Wording comes from `change_ana`: "+12 on last week", "6 fewer than last week", "Same as last week".
- **Tiles**: Actions, then the three busiest types (ties and empty types in table order), each in its own colour, with a sparkline.
- **Day by day** (columns; "Week by week" for All time or a range over 31 days), **By time** (donut and key, see below), **By type** (donut and key). Each type has one colour everywhere: Approvals clay, Leads and people teal, Notes sage, Emails slate, Gold ochre, Memberships plum. (Who did what was removed on 2026-11-13: By time took its place; the Staff member filter stays.)
- **By time** (2026-11-13): how many staff actions happened in each part of the London day, by the clock on the wall (summer time followed), a ring like By type with the busiest part in the centre ("Busiest" over "Morning"; "0 actions" when empty), so it does not repeat the By type total and a key of colour, name and hours, count and share. Morning 06:00 to 11:59 (ochre), Afternoon 12:00 to 16:59 (teal), Evening 17:00 to 21:59 (plum), Night 22:00 to 05:59 (slate; an action at 02:00 belongs to night of its own calendar day, not the day before). The colours are existing Office tokens; all six Office hues are already type colours, so these four are reused on a separate card. A line above says where most happens ("Most of it happens in the afternoon: 48 of 107."); a tie goes to the earlier part. It obeys When, Dates, Staff member and Type like everything else, and has the same empty state as By type. Like By type it has no table view.
- **Everything that happened** sits straight under the tiles (above Day by day, on the computer and the phone). Closed, it shows the 8 newest actions with their day headings; "See all" (a plain link, `?all=1`; it reads "Show less" when open) opens the whole list, 10 rows a page (`activity.OPEN_PAGE_SIZE`, fixed, not a setting; page 1 is rows 1 to 10, the closed 8 are only a preview) with the shared pagination under it (`common/_pagination.html`, `?all=1&page=N`, the opened state kept). The page count is the stored total divided by 10, not a count over the sources; a page past the end is the last page, garbage is page 1. Every page starts with its own day heading. Paging is seamless with script (`common/js/pager.js`: fetches `?fragment=1`, swaps `#act-list` and the pager, pushes the address, handles Back; scrolls to the card heading only when it is above the view, jumps under reduced motion; failure is a normal load); without script the links land on `#list`. With 8 or fewer there is no See all. The true total sits by the heading. A range or filter change updates both parts and keeps the open state (the form carries `all=1`) and goes back to page 1. Newest first. Day headings (Today, Yesterday, Mon 9 Nov, with the year when it is not this one) carry the true count of that day.

The list and the stored totals use one filter (`_scope`, counted by `_by_day`), so per-person, per-type and per-day counts equal the rows once the totals are refreshed.

## Stored figures (owner rule: PROJECT.md, last line)

Tiles, change lines, Day/Week by day, By type, the staff dropdown and the day counts in the list's headings (and the total by "Everything that happened") are read only from `office.ActivityDay`: one row per London day, type (`group`) and staff member (`staff_key`, the normalised email, with `staff_label` the fullest label that day) and a `count`. Unique on (day, group, staff_key), index on day; counts only, no names of people, no text. A page load makes two small reads of it (the range, the period before) plus one for the staff list; no source table is counted. A line under the tiles says "Figures update every hour, the list is live."

**By time** is read only from `office.ActivityTimeOfDay` (added in `office/0004`, a new table, `ActivityDay` is unchanged): one row per London day, part (`morning`, `afternoon`, `evening`, `night`), type and staff member (`staff_key`) and a `count`. Unique on (day, part, group, staff_key), index on day; counts only, no names, no text. A page load adds one small grouped read of it (at most four rows back). The hour is taken in the database in the London zone (`ExtractHour(tzinfo=...)`, in `activity._by_day_hour`), the same on SQLite and Postgres, then `activity.part_of_hour` picks the part. It is filled by exactly the same paths as `ActivityDay` (below), in the same transaction, with the same safeguards, and the no-wipe guard is applied to each table on its own.

- **Filled by** (both tables): the hourly roll-up and the debounced refresh after an event (`snapshots.build_everything` calls `activity_store.refresh_recent`), which recount only today and yesterday with the same per-source counting the list uses. A failure there is logged and never stops the other figures.
- **Asked for by**: `office/signals.py` calls `snapshots.request_refresh()` (debounced, after commit) whenever a staff row is saved or deleted in any source: notes and note events, person edits, archive and genuine events, the approach list (added and done), emails, membership decisions, Gold staff events, and the four manual membership kinds. Rows with no staff label or an automatic label ("Group email", "Bounce", "His own link") and other System events do not ask. Before this, only approvals, archive and genuine marks, and approach list adds asked; notes, edits, done, emails, Gold and manual membership events did not.
- **Older days**: a delete or cascade (a person removed from the approach list or erased, a deleted Gold application), a backdated save or a moved time marks its London day (and the old day when the time moved) in `ActivityDirtyDay`. The days of one transaction are collected in memory and written once when it commits (one row per day); the next refresh recounts them, each once (a long run of marked days is recounted as one span), then clears the marks it covered. Nothing is recounted inside the request.
- **Nightly**: `office.activity_store.scheduled` ("activity-rebuild", 04:45, `register_schedules`) is a full recount, a safety net for anything the marks missed.
- **Rebuild**: `python manage.py rebuild_activity` recounts the whole history (`--dry-run` writes nothing and prints totals, every row as "day · type · staff: before → after", the days covered, totals by type and by staff, then the By time table in its own section after those (its totals, every row as "day · part · type · staff: before → after", e.g. "5 Nov 2026 · Afternoon · Approvals · Barry Lobenstein: none → 20", and the stored total of each part, old → new), and the command to run; `--summary` prints only the totals; the real run prints the same detail for what it did, and a second run says nothing changed). **Run it once after deploying this (the first run fills the new By time table: until then the ring says no actions)**, and again whenever an old row was added or backdated, or a person was erased (the refresh only recounts today and yesterday, so those days stay as stored until then). It is a command, never a migration; safe to run again.
- **Left live**: only the list "Everything that happened", 50 at a time (the stable key), read from the sources.

## Rows

One sentence in the Dashboard feed row, "Moishe added a note on Hugo", the detail under it (archive reason, old to new, the plan, "Did not send"), the time (24 hour, London) on the right. The person is his name, else his email, a link to his Office page while it exists; erased, "a removed person". The staff name is his first name (from his account, else the first word of a stored name, else his email); when two staff share a first name, full labels are shown. Note text and message bodies are never read into a row, a label, the JSON or the page.

## Sources (each is one table, read for the list and for the counts)

| Type | Source | Rows |
|---|---|---|
| Notes | `StickyNote` (a note copied from a Gold event counts here, once), `NoteEvent` | added, edited, deleted, restored a note |
| Leads and people | `PersonEdit`, `LeadArchiveEvent`, `OutreachEntry` | first name, mobile or email added, changed, removed; archived, moved back, marked genuine, undid it; added to and marked done on the approach list |
| Emails | `PersonMessage` | emailed, tried to email |
| Approvals | `MembershipReviewEvent` | approved, declined, undid the decision |
| Gold | `ApplicationEvent` with a staff label, not Applied, emails or notes | approved, final approval, sent back, declined, replied, contacted, invites, admin status change, guide |
| Memberships | `SystemEvent` kinds `setup_manual`, `setup_edited`, `setup_cancelled`, `sale_restored` | set up, changed, cancelled, restored the sale price |

Left out on purpose: automatic actions (labels "Group email", "Bounce", "His own link"), any action with no staff label, the payment window events (System host actions), removing someone from the approach list (nothing records it), `ArchivedLead` and `GenuineLead` (already in `LeadArchiveEvent`), `Subscription.created_by` and `cancelled_by`.

## Staff

One person is one entry however his label was stored ("Name (email)" from most sources, a bare email from the system audit, an old plain name): the key is the email inside the label, else the label. The select shows the account's own label while the account exists, else the best stored one, and the filter matches the email inside any label. The list is built only when the page is rendered whole, from the distinct stored labels (one query) and the accounts (two light reads), never for the Show more rows.

## Paging

Paging is by offset over the merged sources. For page N each source returns its newest 8 + N x size + 1 matching rows (`-when, -pk`); they are merged by (time, source, pk), the same order the database has, and the page is the slice. That costs more on a deep page, which is fine at this size, and a page never repeats a row within one load. Rows are built for the slice only. The figures are not counted here: they are read from the stored totals (see above).

## Empty states

No actions in the range: charts say "No staff actions in this range." and the tiles show 0; the list says "Nothing happened in this range." with "See all time". Filtered with no results: "Nothing matches that. Try fewer filters." with Clear. Nothing ever: "No staff activity yet."

A nightly job (`activity-rebuild`, 04:45 London) recounts the whole history too, so older days fix themselves; `rebuild_activity` is still the one-off after deploy.
