# Feature: Spa 99 System (dev-only business rules)

Branch `feature/system`. Decisions: PROJECT.md rows 2026-10-23 (three staff front ends on one backend; System before Control; recipients move from env to System).

## What it is

`system.spa99.uk` (dev: `system.localhost:8000`): the locked room where developers change the rules the site and, later, the building run on. Same Django project and database, its own app `system`, its own host via the existing host routing. Search engines never see it. Nothing in Office or Control links to it.

## Who gets in

- Developer level or above (the `Developer` group, or a superuser; `common.levels`). Everyone else gets a plain 404 (the host does not admit it exists). The old `System` group is retired.
- Signing in is at `/dev-login/` (2026-10-29; `/login/` is a plain 404 like any unknown path). The lock code is asked on entry ("unlock"; no password again), valid 15 minutes of activity, then asked again. Office/public sign-ins never unlock System.
- Every change is logged: who, when, what, old value, new value, with one-click undo (restores the old value as a new logged change). Uses the existing `django-simple-history` where the model has it; a single `system` change list reads it.

## Look

Compact, dense and calm: small boxes, small controls, tables you can edit in place, a left section list. Different from the Office (not the brand showcase). One small, self-hosted CSS library may be used if it clearly helps (chosen in the design brief, pinned version).

## Rules carried over

- Business rules are data, edited here, never hard-coded.
- Pages read stored rows; nothing heavy computed on page load.
- Settings changes take effect at once (caches cleared on save).
- Works on SQLite and Postgres.

## Built (2026-10-23, foundations; plans, hours, Gold rules and journey screens come next)

**Host and access.** `SYSTEM_DOMAIN` (dev `system.localhost`, prod `system.spa99.uk`), `SYSTEM_URL`; `HostRoutingMiddleware` sends it to `config/urls_system.py`, `X-Robots-Tag: noindex, nofollow`; the startup log line lists the three staff hosts. Allowed: `is_staff` and active and (superuser or `System` group, made by `setup_roles`, which holds no model permissions). Everyone else, anonymous included, gets a plain 404 (`system.permissions`); only `/dev-login/`, `/health/` and `/robots.txt` are open (`/login/` is not: plain 404). The sign-in is the shared `LoginView` with System's own wrong-try wait (see Wrong tries below); a person who may not use System sees the ordinary wrong-password answer. Sign-in sets a session flag, so a session made on another host never counts.

**Unlock.** After sign-in, `/unlock/` asks for the lock code only (no password; being on the page already means a signed-in Developer or superuser; wrong tries escalate, see Wrong tries below). The unlock time is in the session; every System request slides it; 15 idle minutes by default locks again. Both limits are edited in System > Settings > Security (`SiteSettings.lock_idle_minutes` 1 to 240, `max_sign_in_hours` 1 to 72; risky, logged, undoable); `SYSTEM_UNLOCK_SECONDS` and `SYSTEM_SESSION_AGE` are only the fallback defaults. The page gets the seconds left from the server (`data-system-remaining`); activity (mouse, keys, scroll, click, tab return) sends `POST /unlock/ping/` at most once a minute, which slides the window and answers `{"remaining": seconds}` (403 when locked; `peek=1` reads without sliding). The top bar shows a lock icon and 'Unlocked', and the countdown with Stay unlocked only in the last 2 minutes. `POST /lock/` is the Lock button. A System sign-in lasts at most 12 hours by default.

**Change log.** Model `system.SystemChange` (append-only, no history of its own): section, model, object, field, old, new (JSON), kind, who (FK plus email text), `history_id`, `undo_of`. Written by a receiver on django-simple-history's `post_create_historical_record` for the tracked models (`system/changes.py`: SiteSettings, Plan, OpeningRule, Closure, the Gold rule models, journey Question/Option/SuggestionRule, NotificationTemplate; all already had history), so edits made anywhere are listed (no person = "a script"; seed creates with no person are skipped). Team changes (roles, active) have no history and are written directly (`kind=direct`, not undoable). Undo (`services.undo_change`) saves the old value as a new logged change linked by `undo_of`; refused when the field has changed again since, or for created/deleted/team/file entries. Nothing is deleted.

**Undo on a script's change asks for the System code (2026-10-26).** An entry recorded with no person (`services.made_by_script`: no user and no email text; manage.py shell, commands, seed, backfill; shown as "A script changed ...") needs the System code again to undo, in `POST /changes/<id>/undo/` and in Undo all (`/changes/batch/<id>/undo/`, when any open entry in the batch is a script's). A person's change still undoes at once. The view posts `code`; no code gives `403 {"ok": false, "needs_code": true, "message": ...}` and nothing is undone; a wrong code gives the same 403 and writes `undo_code_failed` (failure, outcome failed, "typed the wrong code to undo a script change"); the check is `services.code_matches` (constant time) and counts against the same buckets as `/unlock/` (`throttle.unlock_buckets`, so the two cannot be brute-forced side by side) with the same escalating wait (see Wrong tries below); a wrong try shows the tries left, and a try that starts a wait answers 429 and writes `undo_rate_limited` (blocked) once. A missing code is not a try and is not logged. With no `SYSTEM_UNLOCK_CODE` configured (dev, CI) nothing is asked, as at unlock. The right code undoes as usual: the new change and the `undo` event name the signed-in developer as actor (not a script); the event detail has `script_change: true`; the code is never stored or logged. Migration `system.0010` is choices only (two new event kinds). UI: feed rows carry `needs_code` (and groups `undo_all_needs_code`); those Undo buttons show a small lock icon and title "Needs the System code", and the form has `data-system-needs-code`: `system.js` (`askCodeAndUndo`) opens the shared modal "Enter the System code to undo a script change." (numeric, no autocomplete, Undo / Cancel), posts the code with fetch, shows a wrong-code message inside the modal and stays open, and on success goes to `next`. This path needs JS; without JS a script undo answers the 403 JSON.

**Recipients moved from env.** `SiteSettings.gold_approver_emails`, `gold_approver_cc`, `contact_email` (blank defaults, comma separated lists validated; migration `plans.0007`, schema only). `SiteSettings.contact_address` is what the site and Reply-To use (stored address, else the one inside `DEFAULT_FROM_EMAIL`); `approver_list` / `approver_cc_list` feed `gold.tasks.send_gold_emails` (empty list: nothing sent, logged once, never crashes). ### Review fixes (2026-10-23)

- The 12 hour limit is a hard cap: the System sign-in time is stored in the session and checked on every request (`services.sign_in_valid`); after 12 hours the person is signed out and sent to the sign-in, however active they were.
- `SiteSettings.vat_rate` must be 0 to 100 (validator, `plans.0008`, schema only); VAT, opening date, stage switches and the recipients are passed as `risky_fields` so Settings and Emails confirm old to new.
- `system.middleware.SystemGateMiddleware` (after sessions, before CSRF) answers the plain 404 to anyone who may not be on the System host, so real routes and unknown paths look the same. `/dev-login/`, `/health/` and `/robots.txt` stay open.
- Undo all runs in one transaction with a savepoint per entry: a refused entry (changed again, already undone) is skipped and reported while the others go through; any unexpected error rolls the whole batch back. Undo re-reads the entry with `select_for_update()` (no joins) and refuses when it was already undone.
- A locked POST comes back after unlock to the Referer (same host only) or its section page, never to the POST-only URL.


### Audit log (2026-10-23)

**Two tables, one chain.** `system.SystemChange` (what changed) gains `sentence`, `ip_address`, `user_agent`, `path`; the new `system.SystemEvent` holds security events (a separate table because events have no model/field/old/new, so a `category` on SystemChange would leave most columns empty). Kinds: sign_in, sign_in_failed (System host only; the typed email is kept, a rate-limited attempt is `blocked`), unlock, unlock_failed, unlock_rate_limited, lock_manual, lock_idle (written when the next request finds the unlock expired), sign_out, session_expired (12 h cap), access_denied (one row per IP per hour and 300 an hour in all; method and path only), role_changed, user_deactivated, user_reactivated, undo, undo_all, export, audit_pruned. Each has when, who (FK plus email text), IP (`common.audit.client_ip`, so TRUST_FORWARDED_FOR and the proxy header apply), browser (300 chars), request id (`batch_id`, shared with changes saved by the same request), path, outcome (ok, failed, blocked), section and a small JSON `detail`. Writing an event never raises.

**Sentences.** `system/sentences.py` writes the sentence when the entry is written and stores it ("Changed Tier 1 · Price ex VAT from £299.00 to £319.00"): money, percent, on/off, times, dates, choice labels, list summaries (added/removed). Undo entries read "Put back ...". Team changes read "Changed roles for x from A to A, B". Raw old and new JSON stay.

**Tamper evidence.** Every row has `seq` (one count across both tables), `prev_hash`, `hash` = sha256(prev_hash + canonical JSON of its fields; links to users are not sealed, their email text is). `AuditHead` (one row) holds the newest hash and is locked (`select_for_update`, no joins) while a row is added; SQLite serialises writes. Rows refuse `save()` on an existing row, `delete()`, and queryset `update`, `delete`, `bulk_create`; the admin is read only with no delete action (and a CSV export action). `manage.py verify_audit_log` prints OK, or the first broken row (edited, missing number, or missing newest row) and exits 1. A database-level trigger was skipped: it would block account deletion (SET NULL) and the prune command, and would be Postgres-only. Rows older than this feature have no `seq`: verify counts them as "not covered" (no backfill).

**Feed.** `system/feed.py` `audit_feed(params, page)`: newest first, paginated by group (25), day then group then items. A group is one save (changes sharing a batch id: summary "who changed N fields in Section") or one event. Filters: `category` (change, security, undo, failure), `kind`, `section` (plus Security and Change log for events), `user`, `q` (sentence, email, IP, path, row, field), `range` or `date_from`/`date_to`. A group lists only its matching items. Fixed query count (tested 5 vs 50 groups). `/changes/` is the page; `/changes/export.csv` (same filters) streams the filtered feed, written to the log as an `export` event first; cells that start with = + - @ are neutralised. Context for the page: `feed` {days:[{date, groups:[{type, key, time, user_label, section_label, count, summary, category, ip_address, user_agent, path, outcome, open_count, undo_all_url, items}]}], page:{number, num_pages, total, has_next, has_previous, next_number, previous_number}}, `params`, `people`, `section_choices`, `category_choices`, `kind_choices`, `export_query`.

**Audit log page (frontend, 2026-10-23).** Template `system/changes.html` (+ `_audit_*.html`), `system-audit.css`, `initAudit` in `system.js`, icons in `img/system-icons.svg` (16 Phosphor regular, MIT). Works without JS (plain GET form, native `<details>`, links). `category` may hold several values (`change,security`); `?entry=<id>` opens the detail drawer (and shows the page holding it), `?focus=<id>#g-<key>` jumps to a group. Groups carry `who`, `verb`, `what`, `icon`, `meta`, `outcome_word`, `undo_total`; changes carry `undone_*` and `blocked_*` (a newer change to the same field: "Changed since 14:40"); days carry `name` and `entries`. Chain status is not shown: nothing stores a last-verified result and a full verify per page load is too costly (the drawer checks the one entry's own hash). Add forms carry `data-system-add`: they never count as unsaved changes.

**Retention.** `SYSTEM_AUDIT_RETENTION_DAYS` (default 0, keep forever; above 0 the daily `housekeeping` job prunes, 2026-10-29). `manage.py prune_audit_log [--dry-run] [--days N]` removes the oldest rows and moves the anchor (`AuditHead.anchor_seq`/`anchor_hash`) to the last removed row; verification starts after the anchor, so pruned history is gone and unverifiable by design, the rest still is. It writes an `audit_pruned` event. Never in a migration (migration `system.0003`, schema only).

### Wrong tries (2026-10-29; `system/throttle.py`)

One rule for `/dev-login/`, `/unlock/` and the script-undo code check; it replaces their old flat limits. After a wrong try the page says "Wrong code. 5 more tries." (the first wrong try; "1 more try" is singular; sign-in: "Email or password not recognised. 5 more tries.", the same words whether or not the email exists). 6 wrong tries in a row (`throttle.FREE_TRIES`; Moishe 2026-10-29): wait 1 minute (429, form disabled, "Too many tries. Try again in 1:00" ticking live, announced once, form re-enabled at 0 without a reload; the seconds are server-rendered so it also reads right without JS). After the wait each further wrong try (no success between) adds a minute: 2, 3, 4 ... capped at 60. Success clears it; 24 hours with no attempt forgets it. While waiting nothing is checked (no password or code is verified) and blocked hits are not counted or logged; one audit row per lockout. Keys: sign-in per (typed email + IP) at 6, per IP at 12 (so spraying emails escalates too) and per email at 50 (so spraying addresses does not help); unlock per (person + IP) at 6 and per person at 12, whatever the address. IPv6 addresses count as their /64; emails are normalised (NFKC, casefold). A good sign-in clears the email+IP and per-email counters, not the per-IP one. Stored in the small table `system.WrongTries` (migration `system.0018`, schema only; hashed keys, forgotten after a quiet day), not the cache, because the DB cache's `incr` is read-then-write. The try is counted BEFORE the code or password is checked, with an atomic `F()` update, so parallel requests get distinct numbers and at most the tries left are verified; the request that reaches the limit takes the wait with a conditional UPDATE only one can win, and the rest are refused unverified. Same on SQLite and Postgres. A page view of the sign-in only shows the address-wide wait; a wait on one email shows on the next post.

### Robustness pass (2026-10-25)

- **Version token (lost updates).** Every System form for an existing row (plans, hours rules, closures, capacity, Gold rules, journey questions, options, suggestion rules, Settings, Emails) carries a hidden `row_token`: `services.row_fingerprint(obj, fields)`, a short hash of the row's editable field values as the page rendered them (chosen over `updated_at`: every row has the values, and Settings and Capacity, two forms on one row, only clash when they change the same fields). `system.forms.VersionedForm` checks it during validation (callable without a request, so the code view reuses it) and again under a row lock in `services.save_form`. A changed row means nothing is saved and the form shows "Changed since you opened it. Reload to see the latest." with status 409. A POST with no token (a script, a test) is not checked; every rendered page carries one. `system.js` already ignores hidden inputs for the dirty check and `FormData` sends them.
- **Bad input is a field error.** `common/jsonshape.py` type-checks JSON before it is used as a set member or dict key (perks, plan points, conditions, plan slugs). Plan points `--5` or a superscript digit no longer raise. Number and money boxes accept only the digits 0-9 ("Use the digits 0-9.").
- **Rules live in the models.** `GoldRule.clean` (threshold at least 1, High not below Medium), `Closure.clean` (end after start), `OpeningRule.clean` (times or offset by kind), `SiteSettings.clean` (slot not shorter than the step). Forms, undo and the code view all reach them through `full_clean`; undo refuses with "The old value now breaks a rule ..." instead of saving a broken state. Undo reads the target row `select_for_update`.
- **Option guard.** An option cannot be switched off if that leaves the question below its `min_choices` (the reverse check on raising `min_choices` stays).
- **Bounds** (model validators, schema-only migrations `plans.0013`, `journey.0004`, `gold.0005`): capacity 1-500, slot length 1-1440, slot step 1-1440, booking notice 0-1440, visits 0-100, booking window 0-365, upcoming limit 1-50, cancel hours 0-720, guests 0-50, order 0-1000, screen 1-50, min choices 0-20, offset 0-720, plan points, Gold points and rule points -1000 to 1000.
- **Dates.** A new opening date cannot be in the past (a past date already saved never blocks other Settings fields); a closure being added cannot already be over.
- **Headers.** `system.middleware.SystemHeadersMiddleware` adds never-cache headers and `Content-Security-Policy: frame-ancestors 'none'` to every response on the System host (the gate's 404 included); static files stay cacheable.
- **Audit.** New event kind `password_changed` (System password change; never the password; migration `system.0007` is choices only). Removing a suppression writes its event and deletes in one transaction, and its button asks for confirmation like closure delete.
- **Django admin** shows `is_staff`, `is_superuser` and `groups` read-only ("Change team access in System > Team"); `createsuperuser` still makes the first superuser.
- **Unlock limit.** Besides 5 per 5 minutes per person and address, 10 per 15 minutes per person whatever the address. The cache is now `DatabaseCache` (table `spa99_cache`, `manage.py createcachetable`, run by `entrypoint.sh` after `migrate` and noted in the README), so all gunicorn workers share the counts. Tests and the e2e keep their dummy or in-memory cache (no table needed). `common.ratelimit.hit` lets a request through, and logs, if the cache is unreachable.
- **Last superuser.** Team set access, remove, deactivate and merge lock the active superuser rows (`select_for_update`, no joins) and refuse a change that leaves none: "Spa 99 must keep at least one superuser." (Postgres only; SQLite serialises writes.)
- **Deferred.** HMAC on the audit hash chain (needs a key kept outside the database); a partial POST that omits a checkbox reads as "off" (normal HTML form behaviour; the pages always send the whole row).

**Counting** (`pages.LinkClickDay`, `pages/clicks.py`): one row per link key (`whatsapp`), London day and source, with a `count`; unique on (key, day, source).
